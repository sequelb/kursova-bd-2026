# РОЗДІЛ 3. РОЗРОБКА ПРОГРАМНОГО КОДУ

## 3.1. Обґрунтування обраної архітектури

Систему побудовано за трирівневою клієнт-серверною архітектурою:

а) *Рівень представлення* (клієнт) — односторінковий вебзастосунок (SPA — Single Page Application), що виконується у браузері користувача;
б) *Рівень бізнес-логіки* (сервер) — REST API, що обробляє запити клієнта, реалізує правила авторизації та взаємодіє з базою даних;
в) *Рівень даних* — реляційна СУБД, що зберігає усі дані системи та виконує тригери і збережені функції.

Обрані технології:

- *Мова програмування сервера:* C# (.NET 9). Обрано за типізацію, вбудовану підтримку ORM (Object-Relational Mapping) та зручну модель контролерів для побудови REST API;
- *Серверний фреймворк:* ASP.NET Core 9 Web API. Забезпечує маршрутизацію HTTP-запитів, автентифікацію на основі файлів cookie, авторизацію за ролями та серіалізацію відповідей у формат JSON;
- *СУБД:* PostgreSQL. Обрано за підтримку PL/pgSQL для тригерів та збережених функцій, відповідність стандарту SQL, а також наявність зрілого ORM-провайдера для .NET (Npgsql);
- *ORM:* Entity Framework Core 9 із бібліотекою EFCore.NamingConventions для автоматичного перетворення назв таблиць та стовпців у формат snake_case;
- *Мова програмування клієнта:* TypeScript. Забезпечує типізацію на рівні клієнтського коду та зменшує кількість помилок під час розробки;
- *Клієнтський фреймворк:* React 18 із бібліотекою React Router v7 для маршрутизації, TanStack Query для управління серверним станом та кешування, Tailwind CSS v4 для стилізації та shadcn/ui для базових компонентів інтерфейсу;
- *Інструмент збірки:* Vite. Забезпечує швидке перезавантаження під час розробки;
- *Менеджер пакетів:* pnpm;
- *Протокол обміну:* HTTP (REST). Клієнт надсилає запити до API серверу, передаючи дані у форматі JSON. Автентифікація здійснюється через HTTP cookie, що автоматично включається у кожен запит.

## 3.2. Структурна модель інформаційної системи

Система складається з двох незалежних компонентів, що взаємодіють через HTTP.

*Серверний застосунок* (backend/) — єдиний проект ASP.NET Core Web API. Обрано плоску структуру (без поділу на Application/Domain/Infrastructure шари) як достатню для масштабу курсової роботи. Основні каталоги:

- Controllers/ — контролери REST API, згруповані за функціональністю;
- Models/ — класи сутностей, що відображаються на таблиці бази даних;
- Data/ — контекст бази даних (AppDbContext) із конфігурацією зв'язків та обмежень;
- Migrations/ — міграції Entity Framework Core, включаючи SQL-код тригерів;
- Dtos/ — класи об'єктів передачі даних (DTO — Data Transfer Object) для запитів та відповідей API.

*Клієнтський застосунок* (frontend/) — React SPA. Основні каталоги:

- src/app/pages/ — сторінки, згруповані за ролями (студент, викладач, адміністратор);
- src/app/components/ — спільні компоненти (Layout, Pagination, DateRangePicker);
- src/lib/ — утилітарні модулі (api.ts — HTTP-клієнт, auth.tsx — контекст автентифікації).

*Програма-завантажувач* (backend/src/LearningPlatform.DataLoader/) — окремий консольний проект .NET, що посилається на основний API-проект для використання спільних моделей та контексту бази даних.

## 3.3. Призначення модулів та компонентів системи

### 3.3.1. Серверні контролери

Контролери є точками входу для HTTP-запитів. Кожен контролер захищений атрибутом авторизації, що обмежує доступ відповідною роллю.

*AuthController* — реєстрація нових користувачів (студентів та викладачів), вхід у систему та вихід. При реєстрації пароль хешується за допомогою PasswordHasher, при вході — перевіряється хеш та створюється автентифікаційний cookie.

*MeController* — отримання інформації про поточного користувача. Додатково перевіряє статус облікового запису та примусово завершує сесію для призупинених користувачів.

*CoursesController* — публічний каталог курсів. Підтримує фільтрацію за категоріями, ціною, рівнем складності та рейтингом, пошук за назвою, сортування та пагінацію. Також надає детальну інформацію про курс, включаючи список уроків та відгуки.

*EnrollmentsController* — запис студента на курс (із створенням оплати в одній транзакції), перегляд власних записів, перегляд уроків, позначення уроків як завершених та скасування завершення.

*ReviewsController* — створення, редагування та видалення відгуків студентами.

*RecommendationsController* — отримання персоналізованих рекомендацій для поточного студента. Викликає збережену функцію PostgreSQL get_recommendations.

*CategoriesController* — перегляд списку усіх категорій (використовується для фільтрів каталогу та редактора курсів).

*AuthorsController* — перегляд публічного профілю викладача та його опублікованих курсів.

*TeacherCoursesController* — CRUD-операції над курсами поточного викладача: створення чернетки, редагування, публікація, зняття з публікації, видалення (лише для курсів без записів).

*TeacherLessonsController* — CRUD-операції над уроками: створення, редагування, видалення, зміна порядку (з використанням двопрохідного алгоритму для уникнення порушення обмеження UNIQUE).

*TeacherAnalyticsController* — аналітика курсу (кількість студентів, дохід, середній рейтинг, відсоток завершення, нещодавні студенти) та часовий ряд записів.

*TeacherReviewsController* — перегляд відгуків на курси поточного викладача з фільтрацією за курсом.

*TeacherEarningsController* — перегляд балансу та історії виплат, створення запиту на виплату.

*TeacherProfileController* — перегляд та редагування біографії.

*AdminUsersController* — перегляд користувачів із фільтрацією за роллю, статусом та пошуком. Призупинення та відновлення облікових записів (із забороною призупинення власного облікового запису та інших адміністраторів).

*AdminFinanceController* — фінансова панель із агрегованими показниками за обраний період, перегляд оплат із фільтрацією, оформлення повернення (в одній транзакції із видаленням запису на курс та каскадним видаленням прогресу й відгуку).

*AdminPayoutsController* — перегляд виплат, зміна статусу (схвалення, відхилення, позначення виплаченим) із валідацією автомата станів.

### 3.3.2. Клієнтські модулі

*api.ts* — централізований HTTP-клієнт. Усі запити до сервера проходять через єдину функцію-обгортку, що додає заголовок Content-Type та cookie автентифікації (credentials: 'include'). При отриманні відповіді 401 або 403 генерується подія для оновлення стану автентифікації.

*auth.tsx* — контекст автентифікації (AuthProvider + useAuth). Зберігає поточного користувача, надає методи login/register/logout. Періодично (кожні 60 секунд) перевіряє стан сесії на сервері, що забезпечує синхронізацію між вкладками браузера та автоматичний вихід при призупиненні облікового запису.

*RequireAuth* — компонент-обгортка для захисту маршрутів. Перенаправляє неавтентифікованих користувачів на сторінку входу та обмежує доступ за ролями.

## 3.4. Опис реалізації функцій системи

### 3.4.1. Автентифікація та авторизація

Автентифікація реалізована на основі файлів cookie (cookie-based authentication) без використання ASP.NET Identity. Рішення обумовлене обмеженнями курсової роботи на кількість таблиць та стовпців — ASP.NET Identity додає 7 таблиць із понад 13 стовпцями до схеми користувачів.

При реєстрації пароль хешується за допомогою стандартного класу PasswordHasher<User>. При вході система перевіряє хеш, статус облікового запису та створює автентифікаційний cookie (ім'я lp.auth, термін дії 7 днів, HttpOnly, SameSite=Lax). API повертає коди 401 та 403 замість стандартних перенаправлень ASP.NET, оскільки клієнтом є SPA.

### 3.4.2. Запис на курс та обробка оплати

Запис студента на курс відбувається в одній транзакції бази даних: створюється запис у таблиці enrollments та відповідний запис у таблиці payments зі статусом «Completed». Тригер trg_payments_balance автоматично оновлює баланс викладача. Повторний запис на той самий курс блокується обмеженням UNIQUE на рівні бази даних.

### 3.4.3. Відстеження прогресу

При позначенні уроку як завершеного створюється запис у таблиці lesson_progress. Тригер trg_lesson_progress_recompute автоматично перераховує поле progress у відповідному записі enrollments. При скасуванні завершення запис видаляється, тригер перераховує прогрес у зворотному напрямку.

### 3.4.4. Повернення коштів

Адміністратор може оформити повернення коштів за оплату. Операція виконується в одній транзакції: статус оплати змінюється на «Refunded», а відповідний запис на курс видаляється. Каскадне видалення автоматично видаляє пов'язані записи прогресу уроків та відгук. Тригер trg_payments_balance перераховує баланс викладача.

### 3.4.5. Пошук та фільтрація

Каталог курсів підтримує комбіновану фільтрацію за кількома критеріями одночасно: категорії (множинний вибір), діапазон ціни, рівень складності, мінімальний рейтинг та текстовий пошук за назвою. Результати підтримують сортування (за датою, ціною, рейтингом, популярністю) та пагінацію.

## 3.5. Опис реалізації елементів інтерфейсу

Інтерфейс побудовано як односторінковий застосунок (SPA) з бічною навігаційною панеллю та верхнім заголовком. Бічна панель адаптується залежно від ролі поточного користувача, відображаючи відповідний набір пунктів меню.

### 3.5.1. Сторінки студента

*Панель навчання* (My Learning) — відображає список курсів, на які записаний студент, з індикатором прогресу для кожного (рис. 3.2). Нижче — блок рекомендованих курсів із можливістю перегляду пояснень алгоритму.

[Рис. 3.2. Панель навчання студента]

*Каталог курсів* (Catalog) — сітка карток курсів із панеллю фільтрів зверху (рис. 3.3). Фільтри включають: випадаючий список категорій із пошуком, діапазон ціни, рівень складності, мінімальний рейтинг та критерій сортування. Параметри фільтрів зберігаються в URL-адресі, що дозволяє ділитися посиланнями та зберігати стан при навігації. Для курсів, на які студент вже записаний, картка відображає відсоток прогресу.

[Рис. 3.3. Каталог курсів]

*Деталі курсу* (Course Details) — повна інформація про курс: назва, опис, ціна, рівень, категорії, автор (з посиланням на профіль), список уроків, відгуки інших студентів та середня оцінка (рис. 3.4). Для незаписаних студентів відображається кнопка «Записатись», для записаних — кнопка «Продовжити навчання» та секція відгуку.

[Рис. 3.4. Сторінка деталей курсу]

*Перегляд уроку* (Lesson Player) — текстовий вміст уроку з бічною панеллю навігації по курсу, що відображає статус кожного уроку — завершений чи ні (рис. 3.5). Внизу — кнопки «Позначити як завершений» / «Скасувати завершення» та навігація «Попередній / Наступний урок».

[Рис. 3.5. Сторінка перегляду уроку]

### 3.5.2. Сторінки викладача

*Панель курсів* (My Courses) — сітка карток курсів поточного викладача з індикаторами статусу (чернетка/опубліковано), кількістю студентів та середньою оцінкою (рис. 3.6). Кнопка створення нового курсу.

[Рис. 3.6. Панель курсів викладача]

*Редактор курсу* (Course Editor) — форма редагування метаданих курсу (назва, опис, ціна, рівень, категорії) та управління уроками: створення, редагування, видалення, зміна порядку кнопками вгору/вниз (рис. 3.7). Кнопка публікації доступна лише для курсів із щонайменше одним уроком. Секція видалення курсу відображається лише для курсів без записів.

[Рис. 3.7. Редактор курсу]

*Аналітика курсу* (Course Analytics) — чотири KPI-картки (записані студенти, дохід, середня оцінка, відсоток завершення), лінійний графік динаміки записів за останні 30 днів та таблиця нещодавніх студентів (рис. 3.8).

[Рис. 3.8. Аналітика курсу]

*Відгуки студентів* (Student Reviews) — список відгуків із можливістю фільтрації за конкретним курсом (рис. 3.9).

[Рис. 3.9. Відгуки студентів]

*Заробіток та виплати* (Earnings & Payouts) — поточний баланс, форма запиту на виплату (з валідацією суми) та таблиця історії виплат зі статусами (рис. 3.10).

[Рис. 3.10. Заробіток та виплати]

### 3.5.3. Сторінки адміністратора

*Фінансова панель* (Financial Dashboard) — вибір діапазону дат (з попередніми налаштуваннями 7/30/90/365 днів), KPI-картки (валовий дохід, повернення, виплати викладачам, очікувані виплати), лінійний графік динаміки доходів та виплат, панель сповіщень (рис. 3.11).

[Рис. 3.11. Фінансова панель адміністратора]

*Управління оплатами* (Student Payments) — таблиця оплат із фільтрацією за статусом та пошуком за іменем студента або назвою курсу (рис. 3.12). Кнопка «Повернути кошти» для завершених оплат із діалогом підтвердження.

[Рис. 3.12. Управління оплатами]

*Управління виплатами* (Teacher Payouts) — таблиця запитів на виплату із фільтрацією за статусом та пошуком (рис. 3.13). Кнопки зміни статусу відповідно до автомата станів (Pending → Approve/Reject, Approved → Mark Paid).

[Рис. 3.13. Управління виплатами]

*Управління користувачами* (User Management) — таблиця користувачів із фільтрацією за роллю, статусом та пошуком (рис. 3.14). Кнопка призупинення/відновлення (неактивна для поточного адміністратора та інших адміністраторів).

[Рис. 3.14. Управління користувачами]
